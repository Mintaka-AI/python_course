Prompting and Verified Engineering Results

Learning goals

  • Separate persistent instructions from changing input.
  • Supply verified facts and explicit limits.
  • Keep numerical calculation in deterministic Python.

1. Instructions and input have different jobs

In a Responses API request, instructions describes how the model should behave. input contains the current task and data. Keeping them separate makes the program easier to review.

response = client.responses.create(
    model=model_name,
    instructions=(
        "Explain only the verified facts supplied by the application. "
        "Do not invent values, standards, safety factors, or approvals."
    ),
    input="Verified stress: 150.0 MPa. Explain the result in two bullets.",
)

2. Calculate before asking for an explanation

def calculate_stress_mpa(force_n: float, area_m2: float) -> float:
    if force_n < 0:
        raise ValueError("Force must not be negative.")
    if area_m2 <= 0:
        raise ValueError("Area must be greater than zero.")
    return force_n / area_m2 / 1_000_000

stress_mpa = calculate_stress_mpa(120_000, 0.0008)

The formula is normal Python, so it can be tested independently. The model receives the verified result only after validation and calculation succeed.

3. Build input from explicit facts

facts = f"""
Calculation: axial stress
Force: {force_n} N
Area: {area_m2} m²
Verified result: {stress_mpa:.1f} MPa
Assumption: uniform axial force over the stated area
Limitation: educational example; no design approval
"""

Labels and units make the context easier to interpret. The model is asked to explain supplied facts, not derive or approve them.

4. Specify the output you need

Describe audience, length, organization, and forbidden claims. For example: “Use three short bullet points for a beginner. Include units and the stated assumption. Do not add a safety factor or claim compliance.” Clear requirements improve consistency.

5. Treat all external text as data

User text, uploaded documents, and retrieved content can contain instructions that conflict with application policy. Do not let untrusted content override the program’s calculation boundaries or request secrets and unauthorized actions.

6. Review generated output

Before displaying or storing the explanation, check that required fields are present, units were not altered, unsupported claims were not added, and the result was not recalculated. For stronger guarantees, use Structured Outputs in the next lesson.

Prompt wording alone is not a safety boundary. Enforce critical restrictions with program logic, validation, allowlisted tools, permissions, and human review.

Try it yourself

Use the example file to explain a verified temperature conversion. Change the calculation function, facts, and units, but preserve the rule that the model may explain rather than calculate.
