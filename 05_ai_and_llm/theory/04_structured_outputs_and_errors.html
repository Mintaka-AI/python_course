Structured Outputs, Errors, and Safe API Boundaries

Learning goals

  • Request typed output with Pydantic and responses.parse.
  • Distinguish a structured response from a function call.
  • Handle OpenAI SDK errors without exposing secrets.

1. Why structured output?

Free-form text is convenient for reading but difficult for a program to validate. Structured Outputs constrain a model response to a declared schema. In the Python SDK, a Pydantic model can describe that schema and client.responses.parse can return parsed data.

from pydantic import BaseModel

class MeasurementExtraction(BaseModel):
    quantity: str
    value: float
    unit: str
    missing_information: list[str]

Every field has a name and type. The schema improves output consistency; it does not prove that extracted numbers or units are correct.

2. Parse a typed response

from openai import OpenAI

client = OpenAI()
response = client.responses.parse(
    model=model_name,
    input=[
        {"role": "system", "content": "Extract only explicitly stated measurement data."},
        {"role": "user", "content": "The applied force is 12.5 kN."},
    ],
    text_format=MeasurementExtraction,
)
measurement = response.output_parsed
print(measurement)

text_format supplies the Pydantic schema. output_parsed contains the parsed model instance when parsing succeeds. The program must still allowlist the quantity and unit, check ranges, and request missing area before a stress calculation.

3. Structured Outputs versus function calling

NeedUse
The application needs a typed model responseStructured Outputs
The model should request execution of application codeFunction calling

Function calling does not execute Python automatically. The application receives the requested tool name and JSON arguments, validates them, calls an allowlisted function, and sends the tool result back to the model. Module 6 develops this workflow.

4. Handle SDK errors

import openai

try:
    response = client.responses.create(model=model_name, input="Say hello.")
except openai.AuthenticationError:
    print("Authentication failed. Check the configured API key.")
except openai.RateLimitError:
    print("The request was rate limited. Retry later according to policy.")
except openai.APIConnectionError:
    print("Could not connect to the OpenAI API.")
except openai.APIStatusError as error:
    print(f"OpenAI API returned status {error.status_code}.")

Catch specific failures and show safe messages. Do not print request headers, the API key, or confidential prompt content. A production retry policy must limit attempts and use delays; do not retry authentication or invalid-input errors blindly.

5. Validate after parsing

  1. Confirm the parsed object exists.
  2. Allowlist quantities and units.
  3. Convert units with deterministic code.
  4. Check physical ranges and required combinations.
  5. Ask for missing data.
  6. Call a tested calculation function only after all checks pass.

6. Cost and operational limits

API requests consume project resources and may be subject to model availability, rate limits, and spending limits. Keep prompts focused, avoid accidental loops, record safe request identifiers and usage where appropriate, and configure project limits in the API platform.

Structured output guarantees shape for supported use cases, not truth. Never pass extracted engineering data directly into a consequential calculation without deterministic validation.
