Concurrency Concepts

Concurrency means a program manages more than one task during the same period. It can improve responsiveness or total throughput, but it does not automatically make every program faster.

Prerequisite: understand functions, loops, and return values. First write and test a correct sequential program; then consider concurrency when measurements show it is useful.

Four ways to organize work

Synchronous: finish one task, then start the next. This is the simplest choice for most calculations.

Threads: threads share one process and are useful when tasks mostly wait for files, devices, or other slow I/O. Python threads require careful coordination when data is shared.

Processes: processes have separate memory and can use multiple CPU cores. They can suit independent CPU-heavy calculations, but moving data between processes costs time.

Async: one thread cooperatively switches between tasks at explicit await points. It is useful for many waiting operations. The next lesson covers its syntax.

Choose from the work, not the fashion

One small beam calculation         → synchronous function
Several independent CPU simulations → processes
Several sensor/file waits           → threads or async
Many network requests               → async (when the library supports it)

This is a decision guide, not Python code.

For example, four independent finite-element jobs may use processes. A spreadsheet calculation with four formulas usually should remain synchronous.

Thread-pool syntax

from concurrent.futures import ThreadPoolExecutor

sensor_ids = ["S-01", "S-02"]

def read_one_sensor(sensor_id):
    return sensor_id, 20.0

with ThreadPoolExecutor(max_workers=2) as executor:
    futures = [executor.submit(read_one_sensor, sensor_id)
               for sensor_id in sensor_ids]
    readings = [future.result() for future in futures]

print(readings)

Expected output: [('S-01', 20.0), ('S-02', 20.0)]. submit() starts independent work and returns a future. Calling result() obtains that task's result, waiting if necessary. Keep each task's input and output explicit.

Safety rule: avoid uncontrolled shared state

Do not let worker tasks append to the same global list or change the same dictionary without a clear synchronization design. Instead, have each task return its own result and combine results in one predictable place.

# Using the list returned by the previous complete example:
results = [("S-01", 20.0), ("S-02", 20.0)]
reading_by_sensor = dict(results)

Expected result: {"S-01": 20.0, "S-02": 20.0}. Each sensor has one complete value, regardless of the order in which workers finish.

Warning: concurrency can create race conditions: results change depending on timing. Never use concurrent tasks for safety-critical control without an appropriate, reviewed design. Measure performance and handle failures from every task.
